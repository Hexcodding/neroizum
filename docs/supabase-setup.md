# Отдельная база для разработки: что нажать

Зачем это нужно. Сейчас все три предыдущие версии продукта настроены на один и тот же боевой Supabase. Любой запуск старой папки пишет в живые данные, а тестовая генерация или выданный на пробу ключ смешиваются с настоящими. Пока платящих клиентов нет, цена ошибки нулевая — поэтому разделить базы надо именно сейчас, а не после первой продажи.

Итог: два независимых проекта Supabase. Один для разработки, где можно ломать что угодно. Второй — боевой, куда попадает только проверенное.

## Шаги

1. Откройте панель Supabase и войдите под тем же аккаунтом, где лежит текущий проект: <https://supabase.com/dashboard>

2. Нажмите создание нового проекта — кнопка «New project» в списке проектов.

3. Заполните:
   - **Name** — `neuroizium-dev`. Имя видно только вам, но по нему потом отличать проекты
   - **Database Password** — нажмите генерацию пароля и **сразу сохраните его** в надёжном месте. Этот пароль понадобится для выгрузки базы, и посмотреть его позже нельзя, только сбросить
   - **Region** — ближайший к вашим пользователям. Из доступных для России обычно разумнее всего Франкфурт
   - **Plan** — бесплатного тарифа для разработки достаточно

4. Дождитесь создания проекта — это занимает пару минут.

5. Откройте настройки проекта, раздел с API-ключами (Project Settings → API Keys). Оттуда нужны два значения:
   - **Project URL** — адрес вида `https://xxxxxxxx.supabase.co` (он в разделе General или Data API)
   - **Publishable key** — строка вида `sb_publishable_...` из закладки «Publishable and secret API keys»

   На новых проектах ключи выглядят так. На старых вместо публикуемого ключа лежит `anon public` в закладке «Legacy anon, service_role API keys» — он равнозначен и тоже подойдёт, но Supabase отключает такие ключи до конца 2026 года, поэтому для нового проекта берите `sb_publishable_...`.

   **Secret keys** (`sb_secret_...`) с этой же страницы в `.env` не попадает никогда: это служебный ключ с полным доступом к данным, и платформа сама передаёт его функциям.

6. Пришлите мне оба значения или впишите сами в файл `.env` рядом с `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Это не секреты: публикуемый ключ задуман открытым, доступ к данным ограничивает защита на уровне строк в самой базе.

7. Отдельно сохраните строку подключения к базе (Project Settings → Database, раздел Connection string). Она нужна скрипту выгрузки `scripts/backup-db.ps1`. **Вот это уже секрет** — в файлы проекта её вписывать нельзя.

## Дальше: схема базы и секреты (этап 3)

### Применить миграции

В панели Supabase откройте SQL Editor и выполните два файла по порядку, каждый целиком:

```
server/db/migrations/0001_core.sql
server/db/migrations/0002_quota_functions.sql
```

Сначала на проекте `neuroizium-dev`. На боевом — только после того, как на разработческом всё проверено.

Отдельно стоит поставить вызов уборки по расписанию (Database → Cron): `select public.cleanup_access_data();` раз в сутки. Без него таблицы сессий, попыток и брошенных резервов растут без предела.

### Задать секреты функций

Edge Functions → Secrets. Все значения обязательные — при отсутствии любого функция откажется запускаться и напишет, какого именно не хватает:

| Имя | Что это |
|---|---|
| `SUPABASE_URL` | Адрес проекта. Задан платформой |
| `SUPABASE_SECRET_KEYS` | Служебные ключи, набором вида `{"default": "sb_secret_..."}`. Задан платформой. **В браузер не попадает никогда** |
| `SUPABASE_SERVICE_ROLE_KEY` | То же самое по-старому, одной строкой. Тоже задан платформой; нужен только если новых ключей у проекта ещё нет |
| `NEUROIZIUM_PEPPER` | Длинная случайная строка. Ею подмешиваются хеши ключей и сессий |
| `NEUROIZIUM_WEBHOOK_SECRET` | Секрет подписи вебхука. Тот же, что вы укажете в платёжной системе |
| `NEUROIZIUM_ADMIN_PASSWORD_HASH` | Хеш пароля админки, не сам пароль |
| `NEUROIZIUM_ADMIN_TOKEN_SECRET` | Отдельная случайная строка для подписи входа в админку |
| `GEMINI_API_KEY` | Ключ модели |
| `NEUROIZIUM_ALLOWED_ORIGINS` | Адреса сайта через запятую, например `https://neuroizium.ru`. Звёздочка недопустима |

Значения с приставкой `SUPABASE_` руками не задаются — платформа подставляет их сама, и имена эти в панели заняты. Вписать вручную нужно шесть: `NEUROIZIUM_*` и `GEMINI_API_KEY`. Сервер берёт служебный ключ из `SUPABASE_SECRET_KEYS`, а если такой переменной нет — из `SUPABASE_SERVICE_ROLE_KEY`, так что подходят и новые проекты, и старые.

Случайную строку удобно получить так (PowerShell):

```powershell
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Max 256 }))
```

Хеш пароля админки считается на вашей машине той же функцией, что и на сервере:

```powershell
npm run admin-hash
```

Скрипт спросит `NEUROIZIUM_PEPPER` и пароль, ввод не отображается, в панель уезжает только хеш. Пароль никуда не пересылается и нигде не сохраняется — потеряете, посчитаете хеш заново для нового.

### Выложить функции

Сначала вход и привязка к проекту, один раз:

```powershell
npx supabase login
npx supabase link --project-ref <идентификатор из адреса проекта>
```

Идентификатор — та часть адреса, что стоит до `.supabase.co`. Затем пять функций:

```powershell
npx supabase functions deploy activate
npx supabase functions deploy generate-plan
npx supabase functions deploy plans
npx supabase functions deploy admin
npx supabase functions deploy payment-webhook
```

`plans` отвечает и за список планов, и за остаток генераций — без неё интерфейс войдёт, но не покажет ни сохранённых планов, ни остатка.

У всех пяти в `supabase/config.toml` стоит `verify_jwt = false`. Это не «без проверки»: у клиента проверяется токен сессии из лицензионного ключа, у админки — подписанный токен, у вебхука — подпись платёжной системы. Встроенная проверка JWT здесь не подходит, потому что регистрации в продукте нет вовсе.

### Проверить, что всё встало

```powershell
curl.exe -i -X POST "https://<проект>.supabase.co/functions/v1/activate" -H "content-type: application/json" -d "{\"key\":\"NZM-AAAA-BBBB-CCCC\"}"
```

Ожидаемый ответ — `401` с текстом «Ключ не подошёл»: значит, функция запустилась, прочитала секреты и дошла до базы. Ответ `500` со словами «Не заданы обязательные секреты» прямо называет, чего не хватает.

Первый настоящий ключ выдаётся в панели управления: `npm run build:admin`, открыть собранную страницу по адресу `/admin`, войти паролем и нажать «Выдать ключ». Для локальной проверки хватит `npm run dev` и адреса `http://localhost:8080/admin` — в разработке панель включена всегда.

## Названия кнопок

Панель Supabase периодически меняет оформление, и подпись может немного отличаться от описанной. Смысл шагов при этом остаётся тем же: создать второй проект, забрать адрес и публичный ключ, сохранить пароль базы. Если название на экране не совпадает — пришлите скриншот, разберёмся по нему.
