# server/http/ — точки входа

Обработчики запросов написаны на обычных `Request` и `Response`. Никакого фреймворка здесь нет, поэтому каждый обработчик проверяется тестом как обычная функция, а файлы в `supabase/functions/` только передают ему собранные зависимости.

## Порядок проверок — и есть безопасность

В каждой точке входа он одинаковый и обратный по «стоимости»: сначала бесплатное, потом дорогое.

1. Предполётный запрос и CORS по списку адресов (`cors.ts`).
2. Кто перед нами — по токену сессии, а не по тому, что клиент сообщил о себе.
3. Лимит частоты.
4. Разбор тела.
5. Квота.
6. Модель.

Так неавторизованный запрос не доходит до платного вызова модели, а перебор ключей упирается в лимит до обращения к базе.

## Правила ответов

**Наружу уходит только то, что мы сформулировали сами.** Ни текста исключения, ни имени модели, ни строки от провайдера. В предыдущей версии в интерфейс попадало «Edge Function returned a non-2xx status code»; тест на это есть.

**Ошибка отвечает на два вопроса:** что случилось и что делать дальше. Тексты — в `server/generation/errors.ts`, здесь только доставка.

**CORS не бывает `*`.** Адрес сверяется со списком из переменной окружения; неизвестному источнику заголовок не выдаётся вовсе.

## Почему план отдаётся потоком

Тридцать постов собираются около минуты. Одним ответом это значит крутящийся индикатор и надежда, что пользователь дождётся — в предыдущей версии люди перезагружали страницу и теряли готовые посты. Формат `stream.ts` — Server-Sent Events: обычный текстовый поток, который читает любой браузер без библиотек. Закрытая вкладка останавливает генерацию, иначе мы платим за посты, которые никто не получит.

## Что проверяют тесты

Помимо обычных сценариев — три вещи, ошибка в которых означает утечку: чужой сайт не получает разрешения CORS, текст промпта не попадает в поток ответа, а ответы на неизвестный и отключённый ключ совпадают до последнего байта.
