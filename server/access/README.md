# server/access/ — доступы и лимиты

Регистрации в продукте нет: администратор выдаёт лицензионный ключ, клиент вводит его один раз.

## Что где лежит

| Файл | Отвечает за |
|---|---|
| `keys.ts` | Выпуск ключа и видимого номера клиента, нормализация ввода, хеширование, сравнение за постоянное время |
| `activation.ts` | Вход по ключу и проверка сессии |
| `rate-limit.ts` | Лимиты попыток по нескольким корзинам одновременно |
| `quota.ts` | Месячная квота: резерв, подтверждение, освобождение |
| `payments.ts` | Подпись вебхука и защита от повторной обработки платежа |
| `hmac.ts` | Подпись строки секретом. Одна реализация на вебхук и админский токен |
| `store.ts` | Что доступам нужно от базы. Реализация на Postgres — в `server/db/` |

## Решения, которые здесь нельзя менять «просто так»

**Видимый номер клиента не связан с ключом.** В предыдущей версии рядом с ключом `NZM-A1B2-C3D4-E5F6` хранился «префикс» `NZM-A1B2-C3D` — он был виден клиенту и уходил в вебхук, раскрывая 7 из 12 секретных символов. Здесь номер клиента — отдельная случайная строка, и тест проверяет, что ни один отрезок ключа в неё не попадает.

**Неизвестный и отключённый ключ отвечают одинаково.** Иначе по коду ошибки перебором выясняется, какие ключи существуют. Отдельный ответ есть только у истёкшей подписки: его нельзя получить, не предъявив верный ключ целиком.

**Попытка записывается всегда, даже удачная.** Считать только неудачные — значит разрешить бесконечный перебор тому, кто иногда угадывает.

**Лимит считается сразу по нескольким корзинам.** Адрес клиента приходит из заголовка, который клиент подставляет сам. Подделав его, злоумышленник обойдёт корзину по адресу — но не корзину по самому ключу и не общий лимит на точку входа.

**Счётчики попыток живут в базе.** В предыдущей версии счётчик входа в админку хранился в памяти изолята и обнулялся при холодном старте, то есть лимита фактически не было.

**Квота списывается после успеха, а резервируется до генерации.** Резерв нужен против одновременных запросов: если считать только подтверждённые генерации, два параллельных запроса на последней генерации месяца пройдут оба. Неделимость резерва обеспечивает функция базы, а не код — см. `server/db/migrations/0002_quota_functions.sql`.

## Как это проверяется

Все хранилища описаны интерфейсами, а тесты работают с их реализациями в памяти (`__fixtures__/memory-stores.ts`). Проверять доступы на живой базе нельзя: ошибка в такой проверке стоит чужого доступа.
