# server/db/ — база данных

Миграции и запросы. Каждая миграция — отдельный файл с номером в имени, применяется один раз и не переписывается задним числом.

Базы для разработки и для боевой версии — разные. В предыдущих версиях все три поколения писали в один и тот же боевой Supabase, и любой запуск старой версии менял живые данные.

## Модель доступа: запрет вместо политик

На всех таблицах включена защита на уровне строк и **не создано ни одной политики**. Для анонимной и авторизованной роли это полный запрет; служебная роль защиту обходит по своей природе, а работает ей только серверный код.

Почему так, а не набор политик: политику можно написать слишком широко и не заметить этого, а отсутствующая политика ошибиться не может. Если позже понадобится прямой доступ клиента к своим планам, политики добавляются отдельной миграцией и ровно на нужные таблицы.

## Почему без клиентской библиотеки Supabase

Запросы идут через встроенный REST-интерфейс обычным `fetch` (`rest.ts`). Библиотека тянулась бы специальным импортом, который понимает только Deno — и тогда серверный код перестал бы проверяться обычным компилятором и запускаться в тестах. Здесь тот же код читают компилятор, линтер и человек.

## Что обязано жить в базе, а не в коде

Резервирование квоты (`0002_quota_functions.sql`). Проверить лимит одним запросом, а потом отдельно вставить запись нельзя: два одновременных запроса на последней генерации месяца прочитают одно и то же число и пройдут оба. Поэтому проверка и вставка выполняются внутри одной функции под блокировкой строки лицензии.

Там же решена вторая беда: если процесс упал между резервом и подтверждением, резерв перестаёт учитываться через час. Иначе одна оборванная генерация держала бы слот навсегда.

## Порядок применения

```
0001_core.sql            таблицы, индексы, запрет доступа
0002_quota_functions.sql неделимый резерв квоты, список для админки, уборка
```

Функцию `cleanup_access_data()` нужно вызывать по расписанию: сессии, попытки и брошенные резервы иначе растут без предела.
